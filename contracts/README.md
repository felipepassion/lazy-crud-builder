# Lazy CRUD contract fixtures

This directory is the **authority** for the shared cross-repository contracts between the Builder
(this repository) and every consuming surface (the `LazyCrudExtension` VSIX and CLI, AI agents,
other tooling). When prose anywhere (specs, docs, chat) disagrees with a file here, **the fixture
wins**.

## Layout

```
contracts/
  schemas/v1/lazycrud.platform.schema.json   JSON Schema of the platform descriptor (contractVersion 1)
  schemas/v1/manifest-v2.schema.json         JSON Schema of the generation manifest v2 (contractVersion 1)
  fixtures/v1/fixture-index.json             index: contractVersion, platformVersion, exit codes, diagnostic codes, file list
  fixtures/v1/lazycrud.platform.json         a valid descriptor for the current contractVersion (layers, registry, attributes)
  fixtures/v1/manifest-v2.json               a valid manifest v2 document written by the production writer
  fixtures/v1/manifest-v1-input.json         a v1 manifest (absolute FullPath entries, empty hashes, one unresolvable path)
  fixtures/v1/manifest-v1-migrated.json      the expected v2 output of migrating manifest-v1-input.json (root C:\lazycrud-fixture\solution)
  fixtures/v1/markers/<Ownership>.<ext>.txt  marker v2 examples for GeneratorOwned and GeneratedOnce in every supported comment syntax
  fixtures/v1/hash-vectors.json              inputs with expected contentHash values (LF/CRLF equivalence, BOM, marker exclusion, unmarked file, changed body)
  releases/<version>.json                    what a release physically is: package ids with the SHA-256 of each .nupkg, platformVersion/contractVersion, the commit that produced them, and whether the public source actually carries that version
```

Fixtures for a previous `contractVersion` stay under their own `fixtures/v<N>/` directory when a
new contract version is introduced; nothing is overwritten in place.

## How the fixtures are produced

Every fixture is generated by the **same code** that writes the real artifacts
(`Lazy.Crud.Builder.Platform.Tool descriptor generate --fixtures contracts`, which runs after the
solution builds):

- `lazycrud.platform.json`: `PlatformDescriptor.ToJson()` over the template registry, the canonical
  consumer layout and the attribute catalog reflected from the shipped `Lazy.Crud.Builder.Application.DTO` assembly.
- `manifest-v2.json` and `manifest-v1-migrated.json`: `GenerationManifest.ToJson()` and
  `ManifestMigration.MigrateV1()`.
- `markers/*`: `GeneratedCodeMarker.Render()`.
- `hash-vectors.json`: `ContentHasher.Compute()`.

The CI check `validate fixtures` regenerates the set in memory and fails when a committed fixture
differs from the current build or does not validate against its schema. `validate tree` runs the
same check as part of the build gate.

## Retrieval without a Builder checkout

- Inside the `Lazy.Crud.Builder.Templates` NuGet package, under `contracts/` (same layout).
- Raw files from the repository:
  `https://raw.githubusercontent.com/felipepassion/lazy-crud-builder/main/contracts/fixtures/v1/<file>`
- The CI artifact `lazycrud-contract-fixtures` of every workflow run.

Consumers pin a `contractVersion` (currently `1`) and the `platformVersion` recorded in
`fixture-index.json`, and run their contract and parity tests against these files rather than
hand-copied schemas.

## Frozen semantics summarized (see the schemas and fixtures for the exact shape)

- Ownership: `GeneratorOwned`, `GeneratedOnce`, `Manual` (no synonyms anywhere).
- Marker v2: an `<auto-generated>` block with `LazyCrud-Marker: v2`, `Generator`, `Aggregate`,
  `Layer`, `TemplateId`, `Ownership`, `GeneratorVersion`, `TemplateVersion` (when known),
  `SourceTemplate`, `Policy`, `Customize`; the directive differs per ownership; excluded from the hash.
- Hash: SHA-256 over the LF-normalized body (leading BOM removed) excluding the leading marker block,
  lowercase hex; `hashAlgorithm` = `SHA-256`; `hashScope` = `body-lf-marker-excluded` or `body-lf`.
- Manifest v2: `schemaVersion` 2, `aggregateName`, `generatedAtUtc`, `generatorVersion`,
  `contractVersion`, optional `solutionRootMarker`, `files[]` with `relativePath` (forward slashes,
  never absolute), `layer`, `templateId`, `templateVersion`, `ownership`, `contentHash`,
  `hashAlgorithm`, `hashScope`; migrated entries may carry `unresolved`, `fileName`,
  `originalPathSha256` and `legacyHash`.
- Exit codes and diagnostic codes: `fixture-index.json`.

## Re-running against a locally rebuilt feed

A package is cached by id and version, so rebuilding `1.1.1` locally does not reach a consumer that
already restored `1.1.1`: NuGet keeps serving the copy it extracted the first time. Delete the
extracted folders of the version under test before restoring again, or the run silently exercises the
previous build:

```powershell
Get-ChildItem "$env:USERPROFILE\.nuget\packages" -Directory -Filter 'lazy.crud.*' |
  ForEach-Object { Join-Path $_.FullName '1.1.1' } |
  Where-Object { Test-Path $_ } |
  Remove-Item -Recurse -Force
```

The E2E harness does this itself before every run. Any other consumer of the local feed has to do the
same, otherwise a fix that is already in the feed appears not to have landed.
