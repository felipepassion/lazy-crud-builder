# Generated code policy

Generated code is an artifact of the compiler, not a source you maintain. This page states who owns each file the generator writes, how you can tell by looking at the file, and what happens when a file is edited anyway.

## Three ownership values

Every file the generator writes is classified with exactly one of these values. The names are canonical across the descriptor registry, the marker header, the manifest, diagnostics and every consuming tool; there are no synonyms.

| Ownership | Meaning | On regeneration |
| --- | --- | --- |
| `GeneratorOwned` | Replaceable. The template is the source. | Regenerated on every run, but only after its current hash is compared with the hash recorded in the manifest. A divergence produces an explicit diagnostic and never a silent loss. |
| `GeneratedOnce` | User-owned after scaffold. The generator only seeds it. | Created when the file does not exist; once it exists it is never overwritten automatically (`LC2005` reports the skip). Delete it to have it scaffolded again. |
| `Manual` | Outside the generator. | Never created, modified or deleted by the generator, under any flag, including force (`LC2010`). |

Ownership is declared per template in the descriptor registry (`templates.registry[].ownership`), so every surface derives it from one published source. A template that has no registry entry has its output treated as user-owned and reported (`LC2004`). A file that exists in a generated location without a manifest entry is treated as user-owned. The full contract is in [Ownership](reference/ownership.md).

## Read the marker before editing

Every `GeneratorOwned` and `GeneratedOnce` file whose type has a safe comment syntax begins with a marker v2 header written by the shared writer (never hand-written by a template). A `GeneratorOwned` C# file:

```csharp
// <auto-generated>
// LazyCrud-Marker: v2
// Generator: Lazy.Crud.Builder
// Aggregate: Products
// Layer: Domain
// TemplateId: domain.command-handlers
// Ownership: GeneratorOwned
// GeneratorVersion: 1.2.0
// TemplateVersion: 1.2.0
// SourceTemplate: Domain/DomainCommandHandlers.tt
// Policy: Regenerated on every run. Do not edit this file: direct edits are overwritten by the next generation.
// Customize: change the template (Domain/DomainCommandHandlers.tt), the entity model, or a user-owned partial/extension file instead of this file.
// </auto-generated>
```

A `GeneratedOnce` C# file carries a different policy so that neither a person nor an AI agent mistakes a user-owned seed for regenerable output:

```csharp
// <auto-generated>
// LazyCrud-Marker: v2
// Generator: Lazy.Crud.Builder
// Aggregate: Products
// Layer: Domain
// TemplateId: domain.command-handlers.seed
// Ownership: GeneratedOnce
// GeneratorVersion: 1.2.0
// TemplateVersion: 1.2.0
// SourceTemplate: Domain/DomainCommandHandlers.tt
// Policy: Scaffolded once and now user-owned. This file will not be regenerated; your edits are preserved.
// Customize: edit this file freely; delete it if you want the generator to scaffold it again.
// </auto-generated>
```

The header uses the comment syntax of the file type (`//` for C#, `/* ... */` for CSS, `@* ... *@` for Razor, `<#/* ... */#>` for T4, `REM` for batch files, `--` for SQL, `#` for PowerShell and shell scripts, `<!-- ... -->` for Markdown and HTML). File types with no safe comment syntax (for example JSON) are written without a marker but are still recorded in the manifest with their ownership. `Manual` files are never marked. The exact format is in [Marker v2](reference/marker-v2.md); examples for every syntax are the fixtures under `contracts/fixtures/v1/markers/`.

The marker is excluded from the content hash, so a change to the header alone (a new generator version, for example) never registers as drift.

## What the generator does before overwriting

Before writing a `GeneratorOwned` file the writer computes the frozen hash of the file on disk (SHA-256 over the LF-normalized body, marker excluded, see [Content hash](reference/hash.md)) and compares it with the manifest. The whole aggregate is inspected before the first write. Each file resolves into exactly one state:

| State | Condition | Action by default |
| --- | --- | --- |
| `verified` | Current hash equals the recorded hash | Overwritten with the regenerated content. A missing or malformed header on a matching body is reported as `LC2009` (a marker problem, not drift) and repaired. |
| `drifted` | Current hash differs from the recorded hash | Protected. `LC2001` (error) names the file, the expected, actual and regenerated hashes and the resolutions. The run exits 7 (`OwnershipConflict`). |
| `unverified` | The file exists but no trustworthy baseline hash is recorded (after a v1 manifest migration, a v1-only marker, or a file that predates the manifest) | The regenerated body is compared with the on-disk body. Identical: the baseline is adopted silently (`LC2008`) and, when the header is missing or v1, only the header is rewritten. Different: protected with `LC2002` (error), a code distinct from drift because nothing proves the file was edited. |
| `missing` | Recorded in the manifest but absent from disk | Regenerated without a drift report. |
| new | No manifest entry and no file on disk | Written and recorded. |

An absent baseline never authorizes a destructive overwrite. Unknown ownership in a migrated manifest is treated as user-owned and reported (`LC2003`).

## The collapse guard: an output that says nothing never replaces one that says something

Drift protection answers one question -- *did a human change this file?* -- and a `verified` file is
deliberately overwritable, because that is what regeneration is for. It therefore cannot see the other
way a good file is lost: a transformation that resolves no model emits the template's static preamble
and stops, and what it offers the writer is a syntactically valid file that declares nothing. The
hashes differ, the state is `verified`, and without a second rule the write goes through.

So before any state is considered, and for every state including `verified`, the writer refuses to
replace a file that carries content with a regenerated body that carries none:

| Term | Frozen meaning |
| --- | --- |
| significant line | A body line that is not blank, not a whole-line comment in the file's comment syntax, and not an import or preprocessor directive (`using`, `global using`, `extern alias`, `@using`, `#...`) |
| contentless body | A body with no significant line. The `reason` reported is `empty`, `whitespace-only` or `no-significant-content` |
| collapse | A contentless regenerated body where the file on disk has at least one significant line |

A collapse is refused with `LC2012` (error). Before that refusal is believed, the pipeline **retries the template that produced it** -- a transformation that loses its model is the same class of transient host failure the pipeline already retries, and the run that first exposed this reproduced the full body byte for byte on the next attempt. A retry that produces content records `LC2013` (warning), leaves the superseded `LC2012` in the record as information, and the run is green with the recovery visible. A collapse that survives every attempt keeps `LC2012` and the run exits 9 (`GenerationDefect`). The diagnostic
names the file, `templateId`, `layer`, `aggregate` and source template, both hashes, the significant
line counts on each side, and the rule id. **No resolution flag overrides it** -- `--force` resolves an
ownership conflict, and a defective transformation is not one. The remedy is to rerun the generation;
in the case this rule was written for, the same sandbox reproduced the full body byte for byte on the
next run.

The rule is conservative by construction: a line it cannot classify counts as content, so a body is
only ever called contentless when every one of its lines is demonstrably not content. It is not a
threshold -- a file that shrinks because an entity was removed still declares something, and is
written normally.

A template whose *correct* output carries no significant content -- a global-usings file, whose whole
body is import directives -- declares `emptyOutputAllowed` in the platform template registry and is
exempt. The seven global-usings templates are the ones that declare it today. The declaration is
explicit and never inferred, and a test asserts that every contentless output in the golden corpus is
covered by one.

## Resolutions

The default resolution, `protect`, leaves every drifted and unverified file untouched, reports every affected file (not only the first) and fails the run. The runner accepts two explicit alternatives:

```powershell
dotnet Lazy.Crud.Builder.Platform.Tool.dll generate --solution . --aggregate Products --resolution force
dotnet Lazy.Crud.Builder.Platform.Tool.dll generate --solution . --aggregate Products --resolution skip-modified
```

| Resolution | Behavior | Diagnostic per file |
| --- | --- | --- |
| `protect` (default) | Nothing is overwritten; the run fails with exit code 7 | `LC2001` or `LC2002` |
| `force` | The drifted or unverified file is overwritten with the regenerated content; the previous content is lost | `LC2006` (warning) |
| `skip-modified` | The affected file is left untouched, every other file is generated, the run succeeds listing the skips | `LC2007` (warning) |

None of the three reaches a collapsed output: `LC2012` is refused before a resolution is consulted.

Build-driven generation exposes the same choice as `-p:LazyCrudResolution=force` or `skip-modified`. No resolution ever touches a `Manual` file or an existing `GeneratedOnce` file.

## What is safe to edit

| File | Ownership | Safe to edit? |
| --- | --- | --- |
| Entity classes under `Aggregates/{Aggregate}Agg/Entities/` (except the two seeds below) | Hand-written model | Yes. This is the input of the compiler. |
| `Aggregates/{Agg}/Entities/{Aggregate}.cs`, `Aggregates/UsersAgg/Entities/User.cs` | `GeneratedOnce` | Yes, it is yours after the first generation. |
| `Aggregates/{Agg}/CommandHandlers/{Entity}CommandHandler.cs`, `Aggregates/{Agg}/Requests/{Entity}DTO.cs`, `Aggregates/{Agg}/Validators/{Entity}Validator.cs`, `{Agg}/{Entity}/Index.razor.css` | `GeneratedOnce` | Yes. Delete the file to have it scaffolded again. |
| Everything under `{OutputPath}` (`LazyCode/` by default), `T4/`, generated Razor pages, generated controllers, generated test files (`*.g.cs`) | `GeneratorOwned` | No. Edits are protected, then lost when you force. Change the template, the model or a partial class instead: see [Safe customization](customization.md). |
| Wrapper templates (`DefaultEntities.tt`, `DefaultCommands.tt`, ...) | Seeded by the runner | Not needed; the runner rewrites a wrapper that differs from the expected include directive. |
| `Program.cs`, project files, your own classes | Yours | Yes. The generator never touches files it did not write. |

Ask the manifest when in doubt: `.lazycrud/manifests/{Aggregate}.manifest.json` answers the ownership of every recorded path, and paths absent from it are user-owned.

## Switching markers off

`GeneratedCodeMarkers` in `lazy.settings` (default `True`) is the kill switch for the marker capability. With `False`, files are written without a header, hashed as a whole body (`hashScope` `body-lf`) and `LC5004` records that the capability is disabled. Drift protection still works; only the human-readable header is gone.

## Legacy files

Files produced by versions before 1.1.1 may carry the historical `<auto-generated>` header of the test templates (recognized as a v1 marker) or no header at all. They are detected as generated but never overwritten on that basis alone: they are `unverified` until the first regeneration proves them identical (adoption) or you resolve them explicitly. See [Migrations](migrations.md).
