# Content hash

`contentHash` is the frozen hash rule (contractVersion 1) shared by generation, drift detection, the manifest, the E2E harness and every consuming tool. One implementation, `ContentHasher` in `Lazy.Crud.Builder.Platform`, is used everywhere in the Builder; consumers reimplement it and verify their implementation against the published vectors.

- Vectors: `contracts/fixtures/v1/hash-vectors.json`
- Also shipped inside `Lazy.Crud.Builder.Templates` under `contracts/` and retrievable raw from GitHub
- When prose and fixture disagree, the fixture wins.

## The rule

SHA-256 over the file body with line endings normalized to LF, a leading UTF-8 byte-order mark removed, and the leading Lazy CRUD marker block removed; the digest is written as lowercase hexadecimal.

Step by step:

1. Read the file as text.
2. If the content starts with a Lazy CRUD marker block (see the boundary rule below), drop the block. The body starts after the newline that terminates the last line of the block.
3. Remove a leading UTF-8 byte-order mark (U+FEFF) from the body.
4. Normalize line endings: every CRLF and every lone CR becomes LF.
5. Encode the result as UTF-8 without a byte-order mark and compute SHA-256.
6. Record the digest as 64 lowercase hexadecimal characters.

Comparison of two hashes is case-insensitive; an empty or absent hash never equals anything.

## `hashAlgorithm` and `hashScope`

Every manifest entry states how its hash was computed so that a consumer can reproduce it without reading Builder source:

| Field | Value | Meaning |
| --- | --- | --- |
| `hashAlgorithm` | `SHA-256` | The only algorithm at contractVersion 1 |
| `hashScope` | `body-lf-marker-excluded` | A leading marker block was found and removed before hashing (files of a type that carries a marker) |
| `hashScope` | `body-lf` | No marker block was removed; the whole LF-normalized body was hashed (file types with no safe comment syntax, files written with markers disabled, or files that simply carry no block) |

A hash is a trustworthy baseline only when `hashAlgorithm` is `SHA-256` and `hashScope` is one of these two values. A v1 manifest hash (raw bytes, recorded after migration as `legacyHash`) is never a baseline.

## Marker block boundary

The marker block starts at the line containing `<auto-generated>` (line 1, or line 2 when line 1 is a bare comment opener such as `/*`, `@*`, `<#/*` or `<!--`) and ends after the line containing `</auto-generated>` (plus a following bare comment closer such as `*/`, `*@`, `*/#>` or `-->`). The body starts after that line's newline. Comment decorations are stripped before the tags are compared, so the rule is the same for every comment syntax. See [Marker v2](marker-v2.md).

Because the block is excluded, a change to the header alone (a different `GeneratorVersion`, a reformatted policy line) does not change the hash and never registers as drift. Marker validity is checked separately from drift (`LC2009`).

## Published vectors

Every vector in `hash-vectors.json` carries `id`, `description`, `fileName`, `input`, `expectedHash`, `hashAlgorithm` and `hashScope`. The Builder's test suite recomputes every vector with the production implementation; the harness uses the same file and defines no expected values of its own.

| Id | Input | Expected hash | Scope |
| --- | --- | --- | --- |
| `lf-body` | A C# body with LF line endings, no marker | `cc6db247356ff1ffcc0fd3f22f803980a082ee7ab3aa5e43748f8616f1da28c6` | `body-lf` |
| `crlf-body` | The same body with CRLF line endings | `cc6db247356ff1ffcc0fd3f22f803980a082ee7ab3aa5e43748f8616f1da28c6` | `body-lf` |
| `marker-excluded` | A marker v2 header (`//` syntax) followed by the CRLF body | `cc6db247356ff1ffcc0fd3f22f803980a082ee7ab3aa5e43748f8616f1da28c6` | `body-lf-marker-excluded` |
| `marker-version-changed` | A different header (generator version 0.9.0) with the same body | `cc6db247356ff1ffcc0fd3f22f803980a082ee7ab3aa5e43748f8616f1da28c6` | `body-lf-marker-excluded` |
| `razor-marker-excluded` | A block-comment (Razor) header followed by the body | `cc6db247356ff1ffcc0fd3f22f803980a082ee7ab3aa5e43748f8616f1da28c6` | `body-lf-marker-excluded` |
| `bom-body` | A UTF-8 byte-order mark before the CRLF body | `cc6db247356ff1ffcc0fd3f22f803980a082ee7ab3aa5e43748f8616f1da28c6` | `body-lf` |
| `unmarked-json` | A JSON document (no safe comment syntax, no marker) | `c56df5892fafa8e612fa40cb875e390ee9bc236450348dbbd557812999cfbf24` | `body-lf` |

The first six vectors share one hash: line endings, a byte-order mark and the header never matter; the body does. The exact inputs are in the fixture; a consumer that reproduces all eight has implemented the rule correctly.

## Computing a hash

```powershell
dotnet Lazy.Crud.Builder.Platform.Tool.dll hash --file src\Products\Products.Domain\LazyCode\ProductsAgg.Filters.cs
```

The command prints `contentHash`, `hashAlgorithm` and `hashScope` for the file, computed exactly as the writer and the drift check compute them.

## Where the hash is used

- The shared writer records it in the manifest for every file it writes (`GeneratedOnce` seeds included, informationally).
- The drift inspector compares the recorded hash with the current hash of every `GeneratorOwned` file before the first write of a run (`verified`, `drifted`, `unverified`, `missing`).
- The unverified resolution compares the hash of the regenerated body with the hash of the on-disk body: identical means adoption (`LC2008`), different means protection (`LC2002`).
- The harness (scenario P4) recomputes the hash of every generated file and asserts it matches the manifest.
