## Context

Lazy CRUD is a domain-to-architecture compiler. Its parts, as they exist in this repository today:

| Role | Artifact |
| --- | --- |
| Input (declarative model) | Entity classes + attributes in `src/Builder/Builder.Application.DTO/Attributes/` (43 files) |
| Compiler (per layer) | `src/ProjectFiles/**/*.tt` (98 template files, 89 of them non-test) with the shared core `src/ProjectFiles/project.tt` (1736 lines) |
| Runtime / standard library | 15 packages: `Lazy.Crud.Builder.*` (11) + `Lazy.Crud.CrossCutting.*` (4) |
| Regenerable artifact | Generated `.cs` under the aggregate layers and `LazyCode/` |
| State | `.lazycrud/manifests/*.manifest.json`, `.lazycrud/cache/*.cache.json` |

The Builder does not generate anything by itself — the VSIX/CLI in `LazyCrudExtension` drives T4 and writes the manifests. That split is why contracts, not implementations, are the deliverable here.

### Evidence gathered before proposing (verified in this repository at `d8bb986`)

Every decision below is anchored to something observed, not assumed.

**E1 — Templates package identity is broken end to end.**
`cli/LazyCrud.Core/Models/SettingsModel.cs:95` and `TemplateSourceResolver.cs:142` default the package id to `Lazy.Crud.Templates`. The Builder ships `PackageId` `Lazy.Crud.Builder.Templates` (`src/Templates/LazyCrud.Templates/Lazy.Crud.Builder.Templates.csproj:5`, version `1.0.1`, self-described "legacy aggregator"). `pack-all.ps1` lists 17 project path entries (15 unique projects; `Builder.Infra.IoC` appears three times) and that project is **not** among them. Neither `lazy.crud.templates` nor `lazy.crud.builder.templates` exists in the local NuGet global-packages folder, while all 15 runtime packages do. Additionally, its MSBuild props ship as `build/LazyCrud.Templates.targets`, which NuGet auto-imports only when the filename matches the `PackageId` — so even when installed, the targets never load.

**E2 — Templates are actually shipped per layer, and the aggregator is dead.**
`Lazy.Crud.Builder.Domain.1.0.35.nupkg` contains 24 `.tt`/`.ttinclude` files under `contentFiles/any/any/LazyCrudTemplates/`, declared in the `.nuspec` `<contentFiles>` block. Each layer `.csproj` packs its own layer folder plus **the same shared files**: `project.tt` and `Tests/Tests.Common.ttinclude` are packed by every layer package to the identical `contentFiles` path, so a consumer referencing two or more `Lazy.Crud.Builder.*` packages receives colliding copies.

**E3 — A second, contradictory template packaging path exists as dead config.**
`Directory.Build.props:28-29` globs `**\*.tt` into `contentFiles/any/any/T4/` for every packable project. No shipped package contains a `T4/` folder, because the package projects hold no `.tt` files under their own directories. The `Lazy.Crud.Builder.Templates` targets file, meanwhile, documents include paths of the form `T4/Domain/DomainCommands.tt`. Two layouts are described, one is shipped, and the resolver probes a third (`contentFiles/any/any/LazyCrudTemplates`, then `contentFiles/any/any`, then `content`).

**E4 — Ownership is a boolean, and only tests carry a header.**
`project.tt:1618` `SaveOutput(string outputFileName, bool recreateFileIfExists = true)` and `project.tt:1638` `SaveOutputToSubFolder(...)` are the only writers. There are 60 call sites across the templates; 48 pass the flag explicitly — `true` at 43 and `false` at 5 (`RequestsDTO.tt:59`, `SteppableRequestsValidators.tt:68`, `AggregateSettingsEntity.tt:17`, `DomainCommandHandlers.tt:167`, `UserEntity.tt:14`). The remaining 12 call sites omit the argument and rely on the default `true`. The only generated-code header in the repository is `Tests.Common.ttinclude:12-16`, emitting `<auto-generated>` for test files only.

**E5 — The write path swallows every exception.**
`project.tt:1638-1655`: the whole body of `SaveOutputToSubFolder` — `CreateDirectory`, `File.WriteAllText`, `GenerationEnvironment.Clear()`, `SelfCleanupTemplate()` — sits inside `try { ... } catch (Exception ex) { }`. A permission error, a locked file or a path error produces no output and no signal. `project.tt` contains six catch blocks in total; `catch { /* ignore malformed project entries */ }` (`:535`) and `catch { }` around `FindType` (`:759`) similarly hide model-resolution failures.

**E6 — Manifest v1 is not portable and not sufficient for drift detection.**
`.lazycrud/manifests/Products.manifest.json` records `"FullPath": "E:\\repos\\felipepassion\\lazy-crud-builder\\..."` — an absolute path from a different machine, committed to the repository. Entries carry `"TemplateName": "Unknown"`, `"Layer": "Redirected"` and `"ContentHash": ""`. `GenerationManifestCore.Create` hardcodes `GeneratorVersion = "1.0"`. There is no ownership field and no template version. `GenerationManifestCore.Load/Save/Delete` each swallow all exceptions (`catch { return null; }`, `catch { }`).

**E7 — The repository disagrees with itself about where the solution root is.**
Both `.lazycrud/manifests/Products.manifest.json` and `src/.lazycrud/manifests/Products.manifest.json` exist with **different** content — two manifest roots for one aggregate.

**E8 — Template output location is not portable to package consumers.**
`GetGenerationOutputPath()` (`project.tt:1707`) resolves settings as `Path.GetDirectoryName(Host.TemplateFile) + "/../../Mods/lazy.settings"`. That holds only when templates live at `src/ProjectFiles/<Layer>/`. For a package consumer, templates land in `<project>/LazyCrudTemplates/<Layer>/`, so the path resolves elsewhere, `File.Exists` fails, and the method returns `string.Empty` — silently redirecting output to the template folder.

**E9 — Publication is unverified, uncredentialed and insecure.**
`.github/workflows/` is empty: no CI, no pack validation, no publish gate. `pack-all.ps1:39` carries a live NuGet API key as a **default parameter value**, committed at `HEAD`; the working tree contains a second, different key. `dotnet pack` failures are collected with `try/catch` and the script never checks `$LASTEXITCODE`. Whether a native non-zero exit becomes a terminating error depends on `$PSNativeCommandUseErrorActionPreference`, which is `False` on the verification machine (PowerShell 7.6.5) — so there the catch never fires, `$failed` stays empty, and the script reports success after a failed pack. The explicit exit-code check is the correct fix regardless of host configuration. `pack-infra.ps1` packs `src/Core/Core.Infra.IoC/Core.Infra.IoC.csproj`, a path that does not exist.

**E10 — Local fallback masks a broken public distribution.**
`TemplateSourceResolver.ResolveNuGet` returns `ResolveLocal(...)` on every failure branch: global-packages folder missing, package directory missing, no version directory. On a developer machine with `src/ProjectFiles` present, NuGet-mode resolution succeeds via local files even when nothing is installed.

**E11 — Real consumers already depend on the current shape.**
Tio-Sam's `Directory.Packages.props` pins `1.0.32` for twelve packages but `1.0.29` for `Application.DTO.Http.Models`, `Application.Validators` and `CrossCutting.Domain` — mixed versions are already in production. It also declares `Lazy.Crud.Builder.Templates` `1.0.1` and carries its **own fork** of the templates project at `src/Templates/LazyCrud.Templates/`. Its `src/Mods/lazy.settings` sets `TemplatesNuGetPackageId` to the non-existent `Lazy.Crud.Templates`, `UseNugetTemplates=False`, and `GenerationOutputPath=LazyCode`. Tio-Sam has five aggregates with manifests (Chamados, NPS, Notifications, Processos, Users).

**E12 — Attribute XML docs are already a shipped contract, with gaps.**
`Lazy.Crud.Builder.Application.DTO.1.0.35.nupkg` ships `lib/net10.0/Lazy.Crud.Builder.Application.DTO.xml` containing 42 `<category>` elements — a non-standard tag the compiler passes through and the extension consumes. Gaps: `SubMenuSection.cs` has no `<summary>` and no `<category>`; `MenuSection` and `SubMenuSection` are documented as attributes but do not derive from `Attribute`; and the 43 files span three namespaces (`...Application.DTO.Attributes` ×5, `...Domain.Attributes.T4` ×15, `...Domain.Attributes.Auth` ×1) while all shipping inside the `Application.DTO` assembly.

**E13 — Documentation drift.**
`README.md` documents ".NET Core 8.0 + Blazor WebAssembly", RabbitMQ and MongoDB/PostgreSQL CQRS as "technologies used", while every package targets `net10.0`. It is a deployment/technology overview, not product documentation for a code generator.

**E14 — The E2E pattern to adapt already exists in the ecosystem.**
CopilotSpeaker/MAIA's `tools/maia-flow.ps1` and `artifacts/agent-studio-parity/e2e-geral.ps1`, plus `.github/skills/e2emaia/SKILL.md`, establish a reusable shape: one orchestrator script, `exit 1` on failure, a single terminal `RESULT: OK (...)` / `RESULT: FAIL (...)` line for agents and CI to grep, a JSON export as the source of truth alongside a human-readable digest, and versioned evidence under `artifacts/<run>/`. This repository has a partial precedent in `build/e2e-products.ps1` (7 numbered steps, `Exit-WithError`) — but it depends on local sources, requires Visual Studio for T4, and duplicates its "Step 7" block.

**E15 — Headless generation does not actually transform anything today, and the whole pipeline is built around the Visual Studio T4 engine.**
The extension's `HeadlessT4Engine.TransformSingleT4Async` (`cli/LazyCrud.Cli/HeadlessT4Engine.cs`) implements "transformation" as `dotnet build <csproj>`. The only generator association written into consumer project files is `<Generator>TextTemplatingFileGenerator</Generator>` (`cli/LazyCrud.Core/Services/TemplateScaffolder.cs:769`, `src/AggregateCreator/AggregateCreator.LegacyScaffold.cs:277`, `AggregateCreator.ManifestAndProjects.cs:387,942`) — a Visual Studio custom tool that a plain `dotnet build` does not run. So a headless "regeneration" can transform nothing and still exit zero.

The rest of the pipeline confirms that the Visual Studio engine is the design centre, not an accident: `src/Service/T4Regenerator.cs:176` transforms via DTE `ExecuteCommand("TextTemplating.RunCustomTool")`, and `src/Service/AggregateT4Pipeline.cs` documents Domain-first ordering, the Domain layer's internal two-phase execution, gating on Domain success, per-aggregate `SemaphoreSlim` serialization, and a `MaxParallelT4` throttle whose stated purpose is to avoid "overwhelming the VS/T4 engine".

**E16 — The Visual Studio toolchain is deterministically discoverable, but the repository does not discover it that way.**
`build/run-t4-templates.ps1:65,97` locates `TextTransform.exe` by recursively enumerating `${env:ProgramFiles}\Microsoft Visual Studio` — slow and fragile. The supported mechanism is present on the verification machine at the canonical location `%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe`, and resolves the tooling exactly: `vswhere -latest -prerelease -find "Common7/IDE/TextTransform.exe"` returns `C:\Program Files\Microsoft Visual Studio\18\Insiders\Common7\IDE\TextTransform.exe`. Critically, **the same query without `-prerelease` returns nothing on that machine**, because the only installed instance is VS 18 Insiders — so discovery that ignores prerelease channels would wrongly conclude the prerequisite is unmet. `vswhere` is referenced nowhere in either repository today.

## Frozen shared contracts

The Builder is the canonical authority for the contracts consumed by `LazyCrud.Core`, the CLI, the VSIX and AI agents. This section is the freeze: the values below are settled for this change so both repositories can apply in parallel without drift. Any later change to them is a `contractVersion` change, not an edit.

**F1 — Descriptor.** `lazycrud.platform.json`, embedded in every package. Carries `schemaVersion`, `contractVersion`, `platformVersion`; `layers[]` with `id`, `projectSuffix`, `projectPattern`, `packageId`, `templatePackageId`, `templateContentPath`, `outputPathPattern`; `templates` with `packageId`, `aliasPackageIds[]`, `version`, `contentRoot` and a `registry[]` of `id`/`layer`/`sourceFile`/`outputPattern`/`ownership`/`templateVersion`/`packageId`/`inPackagePath`; `attributes[]` with `name`, `fullName`, `namespace`, `packageId`, `category`, `applicability`, `overloads[]` and `documentationId`; `capabilities[]`; and `compatibility`.

**F2 — Manifest v2.** Document: `schemaVersion` `2`, `aggregateName`, `generatedAtUtc`, `generatorVersion`, `contractVersion`. Per file: `relativePath` (forward slashes), `layer`, `templateId`, `templateVersion`, `ownership`, `contentHash`, `hashAlgorithm`, `hashScope`. Never any absolute path.

**F3 — Hash.** SHA-256 over the file **body**, line endings normalized to LF, **excluding the Lazy CRUD marker block**. Recorded as `hashAlgorithm` + `hashScope`. Identical in generation, drift detection, the harness and every consuming tool. The marker is validated separately and never contributes.

**F4 — Ownership.** `GeneratorOwned` (replaceable, hash-verified before overwrite), `GeneratedOnce` (created only when absent, then user-owned), `Manual` (never touched). No synonyms in any surface.

**F5 — Marker v2.** One header for both marked ownerships, carrying generator identity, `Aggregate`, `Layer`, `TemplateId`, `Ownership`, `GeneratorVersion` and `TemplateVersion` when available, with **different human/AI directives** per ownership. Excluded from the hash. `Manual` files are unmarked.

**F6 — Exit codes.** One table shared with the consuming surfaces: success, assertion failure, prerequisite unavailable, invalid fixture or sandbox, timeout, contract mismatch, ownership conflict.

**F7 — Host prerequisite.** An installed Visual Studio with T4 text-templating tooling is an official prerequisite for generation in every mode, including headless and CLI. It is declared in the descriptor under `compatibility.hostRequirements` (an additive optional field, so it does not by itself increment `contractVersion`), published in the compatibility matrix, resolved through `vswhere` or the Setup Configuration API including prerelease channels, and reported in every run. Headless means unattended, not Visual Studio-free.

### Cross-repository binding

The extension's OpenSpec (`launch-lazy-crud-public-platform`) is written against the same contracts. Where its wording differs, the canonical Builder field wins and the extension adopts it:

| Extension concept | Canonical Builder field | Note |
| --- | --- | --- |
| platform `packageVersion` | `platformVersion` | One value by construction: all packages share one version source. |
| contract document | `lazycrud.platform.json` | Same document; the Builder publishes it, the extension resolves it. |
| `templateId`, `ownership`, `contractVersion` | identical | Already aligned. |
| per-layer template package + in-package path | `layers[].templatePackageId` + `layers[].templateContentPath` | Aligned; the descriptor also declares the shared templates package. |

Two points where this freeze **changes what the extension currently specifies**, and which its side must adopt:

1. **Hash scope.** The extension's manifest spec hashes "the content as written" with LF and trailing-newline normalization. The freeze (F3) additionally **excludes the marker block**. Without this, every marker-format change would mark every file as drifted across every consumer. The extension must exclude the marker.
2. **Unknown baselines.** The extension's migration spec defaults missing ownership to `GeneratorOwned` and states that an unknown hash "shall not be reported as drifted" — which would permit overwriting a file whose state was never established. The freeze (D13) forbids treating absent metadata as permission to overwrite: unknown-hash files are `unverified`, adopted automatically only when the newly generated body is byte-identical, and otherwise protected.

A third point concerns the host prerequisite (F7). The extension's harness spec has a `headless` tier defined as running "on a machine with no Visual Studio installed". Under this freeze that tier is redefined: headless means unattended — no IDE session a person drives — on a machine that satisfies the platform prerequisite. The distinction its spec draws between a `headless` tier and an `ide` tier remains valid and useful, because the `ide` tier drives a real Visual Studio window and takes over the machine's input, while the headless tier only invokes the installed T4 tooling. Only the "no Visual Studio installed" wording has to change.

The published fixtures (capability `contract-fixtures`) are the tie-breaker: if prose and fixture disagree, the fixture wins.

## Goals / Non-Goals

**Goals:**

- One canonical, machine-readable descriptor that every surface reads instead of hardcoding platform version, layers, package ids, template ids or attribute taxonomy.
- Shared contracts frozen and published as implementation-generated fixtures, so the Builder and the extension can apply in parallel without drifting.
- An ownership model that is explicit in the template, present in the emitted file, and recorded in the manifest — so a human or an AI agent can classify any file before editing it.
- No silent data loss: an externally modified `GeneratorOwned` file is detected by hash and handled by documented, diagnosable behavior — and an absent baseline never authorizes a destructive overwrite.
- No silent failure: every write, template resolution and manifest operation either succeeds or produces an actionable, testable diagnostic.
- Compatible evolution. Existing aggregates in CopilotSpeaker, Tio-Sam and Nutri.Veda keep generating byte-identical output apart from the marker block, with migration and fallback defined per version.
- A public distribution proven as a public distribution — clean room, no local source, no private feed.
- A single unattended command that proves the whole chain with real template transformation through the declared Visual Studio toolchain, reliable exit codes and machine-readable evidence.

**Non-Goals:**

- Rewriting the T4 generator. Accumulated behavior in `project.tt` is the product; it is extracted incrementally, not replaced.
- Making generation independent of Visual Studio. An installed Visual Studio is a declared platform prerequisite, not a dependency to be removed.
- Changing the generated architecture, the layer set or the attribute semantics.
- Implementing the extension/CLI side. This change defines, freezes and validates the contracts and publishes their fixtures; adoption lands in the `LazyCrudExtension` repository under `launch-lazy-crud-public-platform`.
- Migrating away from T4, MSBuild or `contentFiles`.
- Adding new product features to the generated code.

## Decisions

### D1 — The platform descriptor is a generated build artifact, not a hand-maintained file

`lazycrud.platform.json` is produced during build from MSBuild properties and embedded in every package, rather than checked in and edited by hand.

*Why:* E1/E3 show the failure mode of hand-maintained duplication — four descriptions of the template layout, none authoritative. A checked-in file would become a fifth. Generating it makes drift a build failure rather than a runtime surprise. CI validates that the descriptor matches what the packages actually contain (E2), which is the only check that would have caught E1 and E3.

*Alternatives considered:* (a) A checked-in JSON file — rejected: same drift class as today, with nothing enforcing agreement. (b) Deriving everything at runtime by reflecting over installed packages — rejected: clients would need every package installed just to learn which layers exist, and it cannot express compatibility ranges. (c) MSBuild properties only — rejected: not consumable by the VSIX, the CLI or an AI agent without an MSBuild evaluation.

### D2 — Ownership is declared per template, and the marker is written by the shared writer

The ownership value (`GeneratorOwned` / `GeneratedOnce` / `Manual`) is passed at the `SaveOutput*` call site, and the single shared writer emits the matching header. Templates do not hand-write headers.

*Why:* E4 shows ownership already exists as data at those 48 explicit call sites (and implicitly at the other 12); the boolean simply loses its meaning on the way out. Making the writer emit the header guarantees uniform coverage across all 98 templates and prevents the drift where only tests have a header. Concentrating it in the writer also means the manifest, the marker and the drift check derive from one value that cannot disagree.

`GeneratedOnce` gets a **distinct** message. A file seeded once and then owned by the user must never carry "changes will be lost when regenerated" — that text tells an AI agent the opposite of the truth and invites it to discard the user's work.

*Alternatives considered:* (a) Inferring ownership from the filename (`.generated.cs`) — rejected: E4's five `GeneratedOnce` sites produce ordinary filenames, and renaming them breaks existing consumers. (b) A per-template header directive — rejected: 60+ edit sites, each able to drift.

### D3 — Keep `.generated.cs` naming as-is; add `GeneratedCodeAttribute` only where it cannot break consumers

Marker headers are applied everywhere. `[GeneratedCode]` is added only to newly generated types in layers where no consumer reflects over attributes, and never to partial types users extend.

*Why:* The manifests show existing consumers generate files such as `DefaultEntities.generated.cs`, and Tio-Sam has five aggregates of such files. Renaming to `.g.cs` would orphan every existing manifest entry and every `.csproj` glob in the field (E11). `[GeneratedCode]` also suppresses some analyzers and changes reflection results — acceptable for internal plumbing, not for entity types that user code and EF Core inspect.

*Alternatives considered:* Blanket `.g.cs` + `[GeneratedCode]` — rejected on compatibility grounds; it is the aggressive rewrite the relaunch explicitly avoids.

### D4 — Manifest v2 is additive and versioned; v1 is read and upgraded, never rejected

v2 is the frozen shape in F2. A reader encountering v1 (no `schemaVersion`) migrates it in memory and rewrites v2 on the next successful generation.

*Why:* E6 shows v1 is unusable for drift detection — empty hashes and foreign absolute paths. But E11 shows five live Tio-Sam manifests plus whatever CopilotSpeaker and Nutri.Veda hold. A hard schema break would strand them. Migrate-and-rewrite means the first regeneration after upgrading heals the manifest.

**No absolute path is retained, not even for old readers.** An earlier draft kept `FullPath` as a deprecated field so v1 readers would not crash; that directly contradicts the frozen "never absolute" rule and would keep shipping a stale, machine-specific path. `schemaVersion` is the compatibility mechanism instead: a v1-only reader sees `2` and can refuse or migrate, rather than silently trusting a path from another machine.

**Migration never invents data.** An entry whose absolute path cannot be expressed under the current root is retained and marked unresolved, with a warning — not dropped, and not given a guessed path. An entry with no hash records the hash as *unknown* rather than as a match, and unknown ownership is recorded as unknown rather than defaulted to replaceable. Absent metadata is never permission to overwrite; see D13.

Relative paths also fix E7: paths become relative to a solution root the manifest itself anchors, making the two-manifest-roots ambiguity detectable rather than silent.

*Alternatives considered:* (a) A new file next to the old — rejected: two sources of truth, exactly the problem being solved. (b) Hard v2-only cutover — rejected: breaks existing consumers with no migration path. (c) Defaulting missing ownership to `GeneratorOwned` — rejected: it converts missing information into permission to destroy user content.

### D5 — Drift protection defaults to *block and diagnose*, not to auto-overwrite or auto-merge

When a `GeneratorOwned` file's current hash differs from the manifest's last-generated hash, generation **does not overwrite it**. It emits a diagnostic naming the file, both hashes and the resolution options, and fails the run unless the caller explicitly opts into `--force` (overwrite) or `--skip-modified` (leave and continue).

*Why:* The rule the relaunch demands is that human/AI changes are never silently lost. Overwrite-with-a-warning still loses them, because warnings scroll past in an IDE and are invisible to a headless agent. Blocking is the only default where the loss cannot happen by inattention. Three-way merge was considered and rejected as far too large a first step for a generator with no merge infrastructure.

*Trade-off accepted:* This can interrupt a bulk regeneration that would previously have "just worked". `--force` restores the old behavior in one flag, and the diagnostic names it explicitly.

*Alternatives considered:* (a) Overwrite + backup `.bak` — rejected: silently accumulates litter and still surprises the user. (b) Warn and overwrite — rejected: it is the silent-loss behavior with extra text.

### D13 — An absent baseline is `unverified`, and is resolved by content comparison before anything is written

A `GeneratorOwned` file that exists on disk but has no trustworthy recorded hash — after v1 migration, or when only a v1 marker is present — is classified `unverified`, distinct from `drifted`. Before writing, the generator compares the **newly generated body** against the **on-disk body** using the frozen hash rule (F3):

- **Identical** → the file is already correct, no destructive write is possible, so the hash is recorded as the baseline and the run continues silently.
- **Different** → the difference cannot be attributed to either the user or a template change, so the file is protected, an `unverified` diagnostic is emitted, and the run fails unless `--force` or `--skip-modified` is given.

*Why:* This is the decision that makes "absent metadata never authorizes a destructive overwrite" practical rather than paralysing. Treating every unknown-hash file as a hard stop would block the first regeneration of every legacy solution — five aggregates in Tio-Sam alone (E11) — and push users straight to `--force`, which is the outcome the rule exists to prevent. Comparing content first means the overwhelmingly common case (a legacy file nobody touched) heals itself with no prompt, while the genuinely ambiguous case stops.

An `unverified` diagnostic is deliberately a **different code** from drift: reporting "this file was edited" about a file whose history is simply unknown would be a false accusation, and an agent choosing a resolution needs to know which situation it is in.

*Alternatives considered:* (a) Treat unknown hash as "no drift" and overwrite — rejected: this is the extension's current wording and it silently destroys pre-manifest user edits. (b) Treat unknown hash as drift — rejected: false positives on every legacy file, and it trains users to pass `--force` reflexively. (c) Adopt the on-disk content as the baseline without comparing — rejected: it would bless a user's edit as generator output and then overwrite it on the *next* run.

### D6 — Extract logic out of T4 behind a seam, keeping T4 as the caller

Output, ownership, marker emission, manifest writing and diagnostics move into a small, unit-testable .NET library. `project.tt` keeps its public method signatures (`SaveOutput`, `SaveOutputToSubFolder`) and delegates to it.

*Why:* `project.tt` is 1736 lines with no tests; all 98 template files depend on it, and the T4 host makes it nearly untestable in place. Preserving the signatures means the 60 call sites do not change, so the blast radius stays inside one file while the extracted logic gets real tests. This is the incremental path the relaunch requires, and it is what makes the acceptance criteria in the specs testable at all.

*Alternatives considered:* (a) Testing T4 by transformation-and-compare golden files only — kept as a complement, rejected as the primary mechanism: it cannot exercise error paths such as a locked file. (b) A full generator rewrite (Roslyn source generators) — rejected: discards accumulated behavior and breaks every consumer.

### D7 — Fix template package identity with a shim, not a rename

`Lazy.Crud.Builder.Templates` stays the canonical id, is added to the pack list, and gets its targets file renamed to match its `PackageId`. A `Lazy.Crud.Templates` package is published as a **deprecated metapackage that depends on** `Lazy.Crud.Builder.Templates`, so clients defaulting to the old name resolve successfully.

*Why:* E1 is a two-sided mismatch: clients ask for a name the Builder never publishes. Changing only the Builder's id would break Tio-Sam's explicit `Lazy.Crud.Builder.Templates` `1.0.1` pin (E11); changing only the clients strands every deployed `lazy.settings` file that names `Lazy.Crud.Templates` (E11 again). The shim satisfies both without a flag day, and the descriptor (D1) records which id is canonical so surfaces converge over time.

*Alternatives considered:* (a) Rename the Builder package to `Lazy.Crud.Templates` — rejected: breaks existing pins. (b) Patch client defaults only — rejected: cannot reach already-deployed settings files.

The shim is a **dependency-only metapackage**: it carries no template content. Template location is resolved through the descriptor's registry (F1), which names the carrying package and in-package path per template, so nothing needs to read files out of the alias package by id. This resolves what an earlier draft left open.

### D8 — One declared distribution strategy: layer templates in layer packages, shared templates in one package

The descriptor declares the strategy explicitly, ending the aggregator-versus-per-layer ambiguity:

- **Layer-specific templates** stay in their layer's runtime package, declared per layer as `templatePackageId` + `templateContentPath`. This preserves what actually ships today (E2) and matches the per-layer resolution the extension's contract expects.
- **Shared templates** — `project.tt` and `Tests/Tests.Common.ttinclude` — move out of the per-layer packages into the single canonical templates package, which every layer package depends on.
- The dead `**\*.tt` glob in `Directory.Build.props` is removed.

*Why:* E2 shows both shared files are currently packed by *every* layer package to the identical `contentFiles` path — a collision the moment a consumer references two layers, which is the normal case. E3's glob is a second, unused mechanism that would double-pack the moment anyone adds a `.tt` beside a package project. Declaring the strategy in the descriptor removes the guesswork that currently makes the resolver probe three candidate layouts (E3), and keeping layer templates where they already ship avoids a migration no consumer asked for.

### D14 — Visual Studio is an official prerequisite; headless means unattended, not IDE-free

Lazy CRUD for Windows/Visual Studio declares an installed Visual Studio with T4 tooling as an **official, verifiable prerequisite** for generation in every mode, including headless and CLI. Transformation runs through that installation's T4 tooling. "Headless" means no human interaction and no IDE session anyone has to drive — it does not mean the absence of Visual Studio.

The toolchain is located through the Visual Studio Installer's query tool (`vswhere`) or the equivalent Setup Configuration API, including prerelease and Insiders channels, never by hardcoded paths or recursive directory scans. If it cannot be resolved, the CLI and harness fail before transforming anything, with a stable diagnostic and the prerequisite-unavailable exit code.

*Why:* This is the owner's architectural decision, and the code agrees with it. E15 shows the entire pipeline is built around the VS/T4 engine — DTE `RunCustomTool`, the `MaxParallelT4` throttle that exists to avoid overwhelming that engine, the Domain-first gate. The generator association written into every consumer project is `TextTemplatingFileGenerator`, a Visual Studio custom tool. Requiring an installed Visual Studio is therefore not a concession; it is what the product has always done, now stated as a requirement instead of assumed. The analogy is a tool that ships its own surface while relying on toolchain installed on the system.

E16 makes the requirement verifiable rather than hopeful: `vswhere` resolves the tooling deterministically, and the `-prerelease` detail is not cosmetic — on the verification machine the only instance is VS 18 Insiders, so discovery that omits prerelease channels would report the prerequisite unmet on a perfectly valid machine.

*What this replaces:* an earlier draft of this design froze `dotnet-t4` (Mono.TextTemplating) as the mandatory mechanism specifically to make the harness independent of Visual Studio. That premise is withdrawn. Independence from Visual Studio was never a product requirement, and pursuing it would have meant validating generation through an engine that is not the one the product actually uses — a battery that passes against a different transformer proves less than one that passes against the real one. `dotnet-t4` may still be used as an internal implementation detail where it demonstrably reproduces the Visual Studio result, but it is not a premise of IDE independence and it is not a substitute for the declared prerequisite.

*What does not change:* the failure discipline. A plain `dotnet build` is never accepted as transformation, a step that produces none of its declared outputs fails, and an unresolvable toolchain fails early rather than silently degrading. Those rules were the real value of the previous decision and they survive it intact.

*Alternatives considered:* (a) `dotnet-t4` as the mandated mechanism for IDE independence — withdrawn by owner decision; it also risks output that diverges from the VS engine the templates were written against. (b) Keep `dotnet build` and hope the custom tool runs — rejected: E15 shows it does not. (c) Treat an installed Visual Studio as an opportunistic fallback — rejected: that is exactly the accidental-dependency framing the owner ruled out, and it leaves the requirement undocumented and unverified.

### D15 — Contract fixtures are generated by the implementation and published as the tie-breaker

Every frozen contract ships a fixture and a JSON Schema, produced by the same code path that writes the real artifacts, published in a retrievable artifact, and versioned by `contractVersion`.

*Why:* Two repositories applying in parallel will drift if each hand-writes its understanding of a schema — which is exactly how the current `Lazy.Crud.Templates` mismatch arose (E1). A fixture generated by the producing code cannot describe something the producer does not actually emit, and a consumer testing against it detects a contract change as a test failure instead of a runtime surprise. Hash vectors matter most: the frozen hash rule (F3) is easy to implement subtly differently, and a shared vector makes an incompatible implementation fail immediately rather than silently reporting drift on every file.

Fixtures are also the declared tie-breaker when prose and artifact disagree, which removes the need to litigate wording differences between the two OpenSpecs.

### D16 — Credential rotation is an external prerequisite, not a player task

Rotating the leaked NuGet keys requires access to the nuget.org account and cannot be performed by an implementing agent. It is therefore recorded as an external prerequisite with an explicit owner, separate from the implementable task list, and the tasks that *are* implementable — removing the default from the script, reading the key from the environment, and the credential scan — stand on their own.

*Why:* An apply run must not appear semantically blocked by an action no implementer can take. Separating them means a player can complete every implementable task and report honestly that the change is code-complete while one external action remains outstanding, rather than either faking the rotation or stalling.

### D9 — Clean room means: a fresh machine-equivalent, public feed only, fallbacks disabled

The clean-room phase runs in a temporary directory with an isolated `NUGET_PACKAGES` folder, a `nuget.config` that clears all sources and adds only the public feed (or a local folder feed standing in for it), and template resolution forced to NuGet mode with local fallback explicitly disabled.

*Why:* E10 is precise about the failure: `ResolveNuGet` silently degrades to `ResolveLocal`. Any validation run inside this repository, or on any machine with `src/ProjectFiles` reachable, proves nothing. Isolating the package cache also prevents a previously restored package from masking a package that was never published — which is exactly how E1 stayed invisible.

*Trade-off accepted:* A resolver flag to disable fallback is a behavior change in the client. It ships as opt-in and defaults to today's behavior, so only the harness sets it.

### D10 — The E2E harness follows the MAIA orchestrator shape

One entry point script; phases with numeric ids; per-phase status; a machine-readable `summary.json` as the source of truth plus a human-readable `digest.txt`; evidence under `artifacts/e2e/<timestamp>/`; a final single-line `RESULT: OK (...)` or `RESULT: FAIL (...)`; `exit 0` only when every required scenario passed.

*Why:* E14 shows this exact shape already works in the ecosystem for headless agent verification, and the relaunch requires a battery an agent or CI can confirm without opening an IDE. Reusing a proven convention costs nothing and makes the output legible to tooling already written against it. The `RESULT:` line matters specifically because an agent reading a truncated log needs one greppable verdict.

Distinct exit codes (not just 0/1) let CI distinguish "a scenario failed" from "the harness could not run", which are different signals.

### D11 — The intentional-failure scenario asserts the diagnostic, not just the failure

The negative scenario modifies a generated file externally, regenerates, and asserts the run fails **with the specific drift diagnostic naming that file** — not merely that the exit code was non-zero.

*Why:* A test that only asserts non-zero passes when the harness crashes for an unrelated reason, which would certify broken protection as working. Asserting the diagnostic identity is what makes D5 provable.

## Risks / Trade-offs

- **Changing `project.tt` breaks every template at once** → Extract behind unchanged method signatures (D6); land a golden-output regression test comparing generated files for the `Products` aggregate before and after each extraction step; keep each extraction to one concern per task.
- **Drift protection blocks a regeneration that used to succeed** (D5, D13) → A legacy solution has no baseline hash, so its files are `unverified`, not silently overwritten. The content-comparison step in D13 keeps this from being a wall: an untouched legacy file regenerates identically and adopts its baseline with no prompt, so only genuinely divergent files stop the run. `--force` restores the previous behavior and `--skip-modified` continues past it; both diagnostics name the flags.
- **Marker headers change the bytes of every generated file** → Real and unavoidable: the first regeneration after upgrade produces a large diff in consumer repositories. Mitigate by shipping markers in one release, documenting it in the changelog and migration guide, and providing the golden-file test so the diff is *only* the header.
- **Consumers with mixed package versions** (E11) → The compatibility matrix must express ranges, not a single supported version. CI validates the descriptor's declared compatibility range against the actual mixed-pin combination Tio-Sam uses, so the documented matrix is tested rather than asserted.
- **The `Lazy.Crud.Templates` shim permanently doubles the package surface** → Accepted, bounded: publish it deprecated from day one with a description pointing at the canonical id, and set a removal milestone in the release guidance rather than leaving it open-ended.
- **Removing the `contentFiles/any/any/T4/` glob could break an unknown consumer** (D8) → Evidence says no shipped package ever contained that folder (E3), so nothing can depend on it. The clean-room phase verifies the resulting package layout explicitly.
- **Rotating the NuGet key breaks whatever currently publishes** → Rotation is an external prerequisite (D16), so sequence it deliberately: the account holder rotates and stores the replacement as a CI secret, while tasks 1.1-1.3 remove the defaults and add the scan. Neither half waits on the other, and the repository stops carrying a working key regardless of when rotation happens.
- **Headless generation may transform nothing and still pass** (E15) → Transformation runs through the resolved Visual Studio T4 tooling (D14), the toolchain is resolved deterministically and reported, the harness fails with the prerequisite-unavailable code rather than skipping, and a step that produces none of its declared outputs fails the scenario. The battery additionally asserts markers, manifest entries, matching hashes, a successful build and passing generated tests, so a green run cannot mean "the project compiled".
- **Scope is large for one change** → Phased tasks with independent value: the frozen contracts, ownership and markers are useful even if later phases slip; the E2E harness is the last gate and validates whatever landed.
- **The two repositories apply in parallel and diverge anyway** → The freeze plus implementation-generated fixtures (D15) makes divergence a failing contract test rather than a silent runtime mismatch. The two known divergences from the extension's current wording — marker-excluded hashing and unverified-baseline handling — are named explicitly in the cross-repository binding so its side adopts them deliberately.

## Migration Plan

**Phase 0 — Repository security.** Remove the key defaults from `pack-all.ps1` and `publish-all.ps1`, read credentials from the environment, add the credential scan. Rotation itself is the external prerequisite in D16 and runs on the account holder's schedule; neither half blocks the other.

**Phase 1 — Contracts and fixtures, no behavior change.** The frozen hash implementation, the descriptor with its template registry and attribute catalog, the manifest v2 schema with its v1 migrator, and the published fixtures and JSON Schemas. Generation output is unchanged. Consumers see new metadata and can ignore it. **This is the phase the extension repository needs in order to apply in parallel**, so it lands first and its fixtures are published as soon as they are stable.

**Phase 2 — Markers and diagnostics.** The shared writer emits marker v2 and real diagnostics; the empty catches go. First release with a visible diff in generated files. Ships with the migration note and the golden-file regression proving only the marker block changed.

**Phase 3 — Drift and unverified protection.** The four-state model, both diagnostic codes, and the resolution flags. Legacy solutions without a baseline are handled by the content-comparison adoption in D13 rather than a hard stop.

**Phase 4 — Packaging and toolchain.** Templates package identity fixed, its targets file renamed so it actually imports, the MSBuild integration wired so build-driven transformation reaches the Visual Studio T4 tooling, deterministic toolchain discovery implemented with its prerequisite diagnostic, the alias metapackage published, shared templates de-duplicated, dead glob removed, CI added with pack validation.

**Phase 5 — Documentation and clean room.** Public docs rewritten including the frozen-contract reference pages; clean-room validation gates the release.

**Phase 6 — E2E acceptance.** The full harness runs green — positive, compatibility-regression, drift and unverified scenarios — using the frozen semantics and the published fixtures, before the change is considered implemented.

**Rollback.** Phases 1 and 4 are additive and revert by unpublishing the new packages. Phase 2's marker emission is behind a descriptor-declared capability flag, so it can be disabled without reverting code. Phase 3's protection only ever refuses to write, so reverting it cannot have destroyed anything. The golden-output test is the tripwire for all of them: if it fails, the extraction step is reverted rather than patched forward. A contract that has already been published as a fixture is not rolled back silently — it is superseded by a new `contractVersion`, so consumers see the change.

## Resolved contract questions

Every question that touched a frozen shared contract is settled here so that neither repository has to guess during apply.

- **Hash scope and algorithm** — settled as F3: SHA-256, LF-normalized body, marker block excluded, recorded via `hashAlgorithm` and `hashScope`. Chosen over full-file hashing because a marker format change would otherwise mark every file in every consumer as drifted. Published hash vectors make it independently reproducible.
- **Whether the `Lazy.Crud.Templates` shim carries content** — settled in D7: no. It is a dependency-only metapackage; template location comes from the descriptor registry, so nothing resolves files out of the alias by id.
- **Which descriptor wins under mixed package versions** — settled in D1 and the `platform-descriptor` spec: the highest `platformVersion`, with a diagnostic naming every conflicting version and its package.
- **`platformVersion` versus the extension's `packageVersion`** — settled in the cross-repository binding: one canonical field, `platformVersion`, equal to the package version by construction because all packages share one version source.
- **Behavior when a baseline hash is unknown** — settled in D13: `unverified`, resolved by comparing generated body to on-disk body; identical adopts the baseline silently, different protects the file and fails without an explicit flag.
- **Headless transformation mechanism** — settled in D14: the T4 tooling of the resolved Visual Studio installation, which is an official platform prerequisite. Headless means unattended, not Visual Studio-free, and headless generation is never declared unsupported.
- **How the toolchain is located** — settled in D14 and E16: the Visual Studio Installer query tool (`vswhere`) or the Setup Configuration API, including prerelease and Insiders channels, never hardcoded paths or recursive scans, with the resolved instance reported in every run.
- **Aggregator versus per-layer templates** — settled in D8: layer templates ship in layer packages, shared templates in one canonical package, both declared in the descriptor.
- **Authority when prose and artifact disagree** — settled in D15: the published fixture wins.

## External prerequisites

These are outside the implementing player's control and are tracked separately from the task list so that apply is never silently blocked by them.

- **Rotate the two exposed NuGet publish keys** (the one committed at `HEAD` in `pack-all.ps1` and the different one in the working tree) and provision the replacement as a CI secret. Owner: the nuget.org account holder. The implementable half — removing the default, reading from the environment, and the repository credential scan — is in the task list and does not wait on this.
- **Confirm Nutri.Veda's actual dependency shape.** No `Lazy.Crud` package reference was found in the local `nutri-veda` checkout, unlike Tio-Sam. The compatibility matrix must not claim to cover it until its real coupling is confirmed by someone with access to the current source. A task records the verification; the matrix ships covering only what is verified.
