## ADDED Requirements

### Requirement: Frozen marker header v2

Every file the generator writes with ownership `GeneratorOwned` or `GeneratedOnce` SHALL begin with a marker header v2. It is a frozen shared contract, parsed by consuming surfaces, and SHALL contain:

- A standard `<auto-generated>` opening line so existing .NET tooling and analyzers recognize the file.
- `Generator` — the generator/product identity.
- `Aggregate` — the aggregate name.
- `Layer` — the layer id.
- `TemplateId` — the stable template id from the descriptor registry.
- `Ownership` — `GeneratorOwned` or `GeneratedOnce`.
- `GeneratorVersion` — the platform version.
- `TemplateVersion` — the template version when the descriptor supplies one.
- A human- and agent-readable directive stating the editing policy for that ownership value.

The header SHALL be emitted by the shared writer, not hand-written in individual templates. Files classified `Manual` SHALL NOT be marked.

#### Scenario: GeneratorOwned header states edits will be overwritten

- **WHEN** a `GeneratorOwned` file is written
- **THEN** its header declares `Ownership: GeneratorOwned`
- **AND** it states that direct edits are overwritten on the next generation
- **AND** it names where to customize instead

#### Scenario: GeneratedOnce header states the file is now user-owned

- **WHEN** a `GeneratedOnce` file is written
- **THEN** its header declares `Ownership: GeneratedOnce`
- **AND** it states that the file is scaffolding that now belongs to the user and will not be regenerated
- **AND** it does not contain the "changes will be overwritten" wording used for `GeneratorOwned`

#### Scenario: Header carries the full frozen field set

- **WHEN** any marked file is written
- **THEN** its header contains generator identity, aggregate, layer, `TemplateId`, ownership and generator version
- **AND** it contains template version when the descriptor supplies one

#### Scenario: Marker is machine-parseable

- **WHEN** a tool reads a generated file's opening lines
- **THEN** it extracts every frozen field using a documented, stable format
- **AND** the extraction succeeds without parsing the rest of the file

#### Scenario: Manual files are not marked

- **WHEN** a template is classified `Manual`
- **THEN** no marker header is injected into its output

#### Scenario: Every classified output is marked

- **WHEN** the marker coverage check runs over a reference aggregate's output
- **THEN** every file recorded in the manifest as `GeneratorOwned` or `GeneratedOnce` has a valid v2 marker
- **AND** the check fails naming any file lacking one

### Requirement: The marker is excluded from the content hash

The marker block SHALL NOT contribute to `contentHash`. It SHALL be delimited so that the hashing implementation can remove it deterministically, and it SHALL be validated as a separate concern from drift.

#### Scenario: Marker block is delimited for exclusion

- **WHEN** the hashing implementation processes a marked file
- **THEN** the marker block boundaries are identified deterministically
- **AND** the remaining body is what gets hashed

#### Scenario: Marker validation is separate from drift detection

- **WHEN** a file's marker is missing or malformed but its body matches the recorded hash
- **THEN** the file is reported as a marker problem
- **AND** it is not reported as content drift

#### Scenario: Changing only the marker does not change the hash

- **WHEN** a file is rewritten with an updated generator version in its marker and an unchanged body
- **THEN** the recomputed `contentHash` is unchanged

### Requirement: Marker v1 remains recognized for detection

Detection of previously generated files SHALL accept the historical v1 header as well as v2, so solutions generated by earlier versions are still identified as generated.

#### Scenario: v1-marked file is still detected as generated

- **WHEN** a solution generated by an earlier version carries only v1 markers
- **THEN** those files are recognized as generated

#### Scenario: v1 marker alone does not authorize overwrite

- **WHEN** a file carries only a v1 marker and has no recorded hash in the manifest
- **THEN** it is not overwritten on that basis alone
- **AND** it is reported for explicit resolution

#### Scenario: v1 file is upgraded on regeneration

- **WHEN** a v1-marked `GeneratorOwned` file is regenerated after its content is verified
- **THEN** the newly written file carries a v2 marker

### Requirement: Markers respect file syntax

The marker SHALL be emitted using comment syntax valid for the target file type, so adding it never breaks compilation or parsing.

#### Scenario: C# output

- **WHEN** a `.cs` file is generated
- **THEN** the marker uses `//` line comments
- **AND** the file still compiles

#### Scenario: Non-C# output

- **WHEN** a file of another supported type is generated, such as a `.bat`, `.css` or Razor file
- **THEN** the marker uses comment syntax valid for that file type

#### Scenario: Unmarkable file types are still tracked

- **WHEN** no safe comment syntax exists for a generated file type
- **THEN** the marker is omitted
- **AND** the file is still recorded in the manifest with its ownership, and its hash covers the whole body

### Requirement: Existing test-template header is unified

The bespoke `<auto-generated>` header emitted by `Tests.Common.ttinclude` SHALL be replaced by the shared marker so test files and production files follow one policy.

#### Scenario: Test files use the shared marker

- **WHEN** a generated test file is produced
- **THEN** it carries the same v2 marker format as production generated files
- **AND** the previous bespoke header is no longer emitted

#### Scenario: Marker change is the only diff

- **WHEN** generated output is compared before and after adopting the shared marker for the reference aggregate
- **THEN** the only differences are within the marker header block
- **AND** the golden-output regression test asserts this
